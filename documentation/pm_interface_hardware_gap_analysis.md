# Precise Motion Hardware Gap Analysis

This assessment looks only at hardware feasibility for a precise-motion layer in the BLDC firmware. The working assumption is that the VESC power stage drives the user's BLDC motor directly using FOC. In that arrangement, the VESC is the motor drive; ClearPath step/direction and HLFB are not the normal command/feedback path. The relevant physical needs are a suitable FOC power stage, adequate position sensing, enable/fault behavior, home/limit/E-stop circuits, external command I/O, and possibly multiple motor channels. ClearPath signals remain relevant only if a separate ClearPath drive is also part of the machine.

The BLDC repository supports many VESC-compatible boards, not one reference controller. Pin availability, voltage/current limits, connector wiring, sensor supply, CAN, and number of motor channels depend on the selected `HW_HEADER` and the exact board revision. Ratings below are therefore about the checked-in hardware configurations and firmware-visible interfaces; confirm a target board's current schematic and product specification before hardware selection.

## Rating Key

| Rating | Meaning |
| --- | --- |
| **Available** | Present on the board as configured, within that board's electrical and power limits. |
| **Available on selected boards** | Present only on hardware configurations that define the required motor channel or connector. |
| **Add-on required** | Feasible by adding a sensor, signal-conditioning/interface board, separate controller, or external component. The stock connector is not an industrial interface. |
| **Not possible with stock VESC alone** | The stock board cannot provide the requested function at the required hardware/safety level. An external safety controller or a different controller architecture is required. |
| **Not needed for direct FOC** | The physical signal or device belongs to the external-drive ClearPath topology. Direct FOC control can provide the corresponding motor behavior through its own power stage and feedback, subject to its accuracy limits. |
| **Software workaround possible** | The hardware is already present, but equivalent behavior can be implemented in firmware or an application without adding a physical interface. This does not imply that the current firmware implements that behavior or that it is safety-rated. |
| **Unverified; qualify per board** | The repository does not establish the necessary electrical, environmental, EMC, or certification rating. Treat as unavailable for industrial deployment until independently verified. |

## Summary

VESC boards are motor power controllers with board-specific low-voltage sensor and communications connections. For a compatible BLDC motor, the VESC can directly run FOC and therefore does not need a step/direction output to control that motor. FOC also has internal motor-state feedback; an external encoder can provide more precise angular feedback on compatible targets. This makes a direct-drive precise-motion approach plausible, but does not make VESC a uniform industrial servo I/O platform.

For direct FOC, the largest hardware gaps are suitable encoder feedback for the required axis accuracy, protected home/limit/command I/O, hardwired safety-rated STO/E-stop, holding-brake hardware where needed, industrial installation qualification, and availability of enough independent motor channels. External interface/safety hardware can work around many of these gaps. Step/direction and HLFB are not required for the direct FOC path.

If the motor is itself a ClearPath integrated servo, the VESC's phase bridge is not its drive interface. The ClearPath motor is driven through its own configured electronics. To command it from a VESC-based host would require a separate step/direction or other supported logic interface, including suitable line drivers/isolation; do not connect a ClearPath logic input to VESC motor phase terminals.

## Direct FOC Workaround Review

The firmware explicitly supports `MOTOR_TYPE_FOC` and FOC sensor modes including sensorless, Hall, encoder, and HFI. The sensor-port layer supports multiple external encoder/resolver protocols, but availability depends on board pin routing and sensor-port configuration. Therefore, some ClearPath hardware functions have a direct FOC equivalent, while others need external electrical/safety hardware or cannot be made safety-rated by firmware.

| ClearPath-era need | Direct FOC equivalent/workaround | Result and boundary |
| --- | --- | --- |
| Servo power stage and motor command | Use the VESC three-phase bridge to drive the compatible BLDC motor with FOC. The motion layer should send native position/speed/current setpoints; do not translate them to step pulses for that same motor. | **Available, board-specific.** Must satisfy the board's motor, voltage, continuous/peak current, thermal, and regeneration limits. Not for driving a ClearPath motor's logic inputs or arbitrary AC servo. |
| Position/velocity feedback | Select FOC sensorless, Hall, or encoder feedback as appropriate. Sensorless/Hall can be useful for commutation and speed, but high-resolution, repeatable axis position at standstill generally needs an encoder. Put the encoder on the load when motor-shaft position does not represent load position because of gearing, compliance, backlash, or slip. | **Software workaround possible** for motor-angle servo behavior; **add-on encoder required** for precision/load-side feedback. Existing encoder drivers do not guarantee every board routes every protocol. |
| ClearPath `Move`/velocity profiles | Generate trajectories in firmware and feed the FOC motor's native control loop. No physical step/direction pulse interface is needed for the directly connected BLDC motor. | **Software workaround possible.** Existing FOC is the actuator/current loop, not a point-to-point trajectory planner. Units, unwrapped position, acceleration, limits, and completion still require software work. |
| ClearPath HLFB at-target or measured output | Derive ready/moving/at-target from encoder feedback, FOC state, faults, and explicit position/velocity tolerances. Use CAN/UART/USB or an external PLC I/O module to export status if another device needs it. | **Software workaround possible** for local status. There is no universal HLFB pin, and synthesized status is not a safety output. |
| ClearPath step/direction input/output | Not needed when FOC directly drives the BLDC. If a separate ClearPath drive must be commanded, use an external PLC/motion controller or pulse generator with the required line driver and isolation. | **Not needed for direct FOC; add-on required for external ClearPath.** The VESC phase outputs must never be treated as logic pulse pins. |
| Home and travel limits | Add switches/proximity sensors through protected, isolated digital inputs or a PLC/remote-I/O module; communicate their states over a supported interface. A custom low-voltage GPIO connection is possible only where the exact board exposes a safe, unused pin. | **Add-on required** for robust industrial sensing. Firmware can implement homing/soft limits once inputs and reference sensing exist. Software soft limits alone cannot detect travel past a bad/stale reference or a sensor/mechanics failure. |
| Operator command inputs (selector, trigger, analog) | Use an external industrial I/O module or PLC and send validated setpoints/requests over CAN/UART. A board's ADC/GPIO can serve a prototype with a suitable front end. | **Add-on required** for 24 V digital, protected outputs, 0-10 V, 4-20 mA, or isolation. Software can map/scaling-filter the values once acquired. |
| E-stop and STO | Use an independent safety relay/controller to command a board-specific hardware gate-disable path only if the board's schematic and safety design support it, and/or remove motor-bus energy with a rated contactor. The safety chain must not depend on the FOC task, ordinary CAN, or a firmware state transition. | **Add-on required** for functional machine E-stop. **Not possible with stock VESC alone** to claim certified STO; an external safety architecture or certified drive is required. External energy removal is not automatically equivalent to STO and needs system-level validation. |
| Holding brake | FOC can apply closed-loop holding torque while control power, feedback, and the power stage are healthy. Add a spring-applied mechanical brake and external brake driver for power-off holding or safety-related load retention. | **Software workaround possible** for powered active hold; **add-on required** for mechanical fail-safe holding. Active torque is not a holding brake. |
| Two or more axes | Use a board with two independent FOC power stages for two motors, if supported; otherwise use multiple VESCs over CAN or a supervisory controller. | **Available on selected boards** for two channels; **add-on required** for more. Distributed controllers need explicit synchronization and common safety behavior; CAN connectivity alone does not guarantee deterministic coordinated motion. |
| Industrial supply, wiring, and environment | Supply the VESC from a properly rated DC bus and use external fusing, disconnects, enclosure, connectors, shielding, and signal isolation as the machine requires. | **Add-on/board selection required.** VESC is not a direct mains-input drive; exact DC ranges and installation ratings are board-specific and require vendor verification. |

### Position-Sensor Limitation

FOC can estimate rotor angle without an encoder, and Hall feedback is available on many boards. Those modes address commutation and motor operation; they do not establish precision over a full mechanical axis travel, especially at zero/very low speed or when the load can move independently of the rotor. The FOC position loop uses angular error, and the ordinary position path normalizes angle. A TS5700N8501 multi-turn encoder mode exists, but a motion implementation must preserve/use the unwrapped reading correctly. Thus, an encoder is a practical hardware requirement for ClearPath-like precision positioning even though it is not required for basic sensorless FOC operation.

No firmware-only addition can create the missing hardware certification. |
| ClearPath step/direction command output | **Not needed for direct FOC; add-on for external ClearPath** | Direct FOC commands the BLDC through the VESC phase bridge, so no step/direction signal is involved. If a separate ClearPath drive must be commanded, VESC boards have no standard step/direction connector; use an external pulse generator/PLC and suitable line driver/isolation. VESC phase outputs cannot be used for logic pulses. |
| ClearPath HLFB feedback input | **Not needed for direct FOC; add-on for external ClearPath** | Direct FOC derives motion feedback from the configured motor sensor and internal state. No generic HLFB connector is defined; an external ClearPath requires an input adapter with appropriate voltage handling, polarity, isolation, and filtering. HLFB-derived status is not a safety output. |
| Digital selector, trigger, and enable I/O | **Add-on required for industrial field voltage; low-voltage GPIO is board-specific** | Hall/encoder pins, UART pins, ADC pins, and a few board-specific GPIOs are not a general industrial digital-I/O bank. 24 V PLC inputs, protected outputs, and configurable isolated channels require an external I/O module. Reuse of sensor pins may conflict with commutation or encoder hardware. |
| Analog command input (0-10 V or 4-20 mA) | **Add-on required** | Some targets expose ADC inputs for low-voltage analog sensors, but the checked-in hardware contract does not promise protected 0-10 V or 4-20 mA input ranges, galvanic isolation, industrial accuracy, or channel availability. Add an appropriate analog front end and verify the target's ADC pin mapping and range. |
| Analog/PWM torque or velocity command output | **Add-on required for external equipment** | The VESC's PWM hardware is primarily assigned to the three-phase power bridge. Some MCU pins may be available on a board, but the configurations do not define a universal industrial analog/PWM command output. Use an external signal-conditioning/output module for a ClearPath or other drive input. |
| Mechanical holding brake output | **Add-on required** | The motor bridge can apply electrical braking within its electrical and thermal limits, but the reviewed target interface does not provide a standard brake-coil power output. A mechanical holding brake needs an external appropriately rated driver, supply, wiring, and interlock design. Electrical braking is not a substitute for a holding brake or safety brake. |
| Two independently driven motor channels | **Available on selected boards** | The firmware contains dual-motor support and several targets define `HW_HAS_DUAL_MOTORS`, including VESC Duet and Stormcore boards. Most targets do not have two independent power stages. A dual-motor board is not itself a gantry or coordinated-axis safety system. See [Duet dual-motor declaration](../hwconf/vesc/duet/hw_duet_core.h#L20) and [Stormcore dual-motor declaration](../hwconf/stormcore/100D/hw_stormcore_100d_core.h#L20). |
| More than two axes | **Add-on required** | Additional VESCs/drives and axis wiring can supply more motor channels, but that is a distributed multi-drive hardware system, not a single-board capability. Network isolation, power distribution, common-stop behavior, and synchronization must be designed at machine level. |
| CAN/UART/USB communication | **Available on selected boards** | CAN is the usual VESC inter-controller interface where the selected board includes it; UART and USB are also board/configuration dependent. Some target definitions explicitly omit CAN. These connectors do not by themselves establish an isolated CAN/CANopen, RS-485, EtherCAT, or industrial Ethernet physical interface. See [generic CAN pin defaults](../hwconf/hw.h#L532), [CAN-equipped Duet pins](../hwconf/vesc/duet/hw_duet_core.h#L327), and [targets without CAN](../hwconf/other/hw_gesc.h#L30). |
| Industrial power input and installation | **Available only within each board's rating; otherwise add-on/replace hardware** | VESC targets have different DC bus voltage and current limits; the motor supply must stay within the exact board's limits. The firmware does not establish direct AC-mains input, a universal 24 V control supply, panel-mount terminals, input isolation, or an industrial enclosure. Use a suitable external DC supply/protection and installation hardware, or choose a drive designed for the required industrial supply. |
| EMC, isolation, environmental and machinery qualification | **Unverified; qualify per board/system** | The hardware configuration headers describe MCU pin routing and electrical limits but do not establish ingress protection, industrial EMC immunity/emissions, vibration rating, galvanic isolation, safety integrity, or a machine certification. Absence of those claims in this repository is not proof that every board lacks a rating; obtain manufacturer documentation and perform system qualification before industrial use. |

## What Is Already Physically Useful

- A compatible motor power bridge with current/voltage feedback and driver protections, subject to the exact board's ratings.
- Three Hall inputs on many targets, and timer-routed incremental encoder support on many targets.
- Sensor-port pin groups that can support specific external SPI/SSC/BiSS-C, ABI, sin/cos, or resolver interfaces on compatible board variants.
- CAN/UART/USB and ADC pins on many targets, with explicit exceptions and pin multiplexing.
- Dual motor power channels on a limited set of board configurations.

These capabilities make a hardware-add-on path plausible for a machine using VESC as the drive for a compatible BLDC/PMSM. They do not make the hardware interchangeable with a ClearCore controller or an industrial servo drive.

## Hardware Decisions Needed Before Design

1. Name the exact VESC board and revision, motor model, supply range, peak/continuous torque/current, and thermal duty.
2. Decide whether VESC will drive its own compatible BLDC/PMSM, or command a separate drive such as ClearPath. These are different power and signal architectures.
3. Select the encoder and verify board pin mux, voltage level, encoder supply, cable length, shielding, maximum edge/data rate, and loss-detection behavior.
4. Define the home/limit/E-stop circuits, including normally-open/closed convention, line fault detection, isolation, and machine-level safety response.
5. Decide whether isolated 24 V I/O, 0-10 V/4-20 mA, mechanical brake control, RS-485, or industrial Ethernet is required; budget external interface hardware for each.
6. Obtain manufacturer board documentation and safety/EMC/environmental evidence. Firmware source alone is not a qualification record.

This assessment rates hardware feasibility only. It does not establish that the motion software, board combination, or completed machine is safe or industrially qualified.
